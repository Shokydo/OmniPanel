# Переезд OmniPanel на Rust — где мы сейчас

Версия панели на диске: **1.26.0**. Ничего в рабочей панели не сломано:
переезд идёт рядом, отдельным Rust-ядром, и подключается только тогда,
когда очередной кусок проверен тестами.

### Мост «интерфейс → Rust»: `ui/tauri-bridge.js`

Собирается автоматически из `preload.js`:

```
node tools/gen-tauri-bridge.js
→ мост собран: ui/tauri-bridge.js
  всего методов: 153 (команды 130, события 21, отправка 2)
```

Это важно: интерфейс не переписывается. В `ui/app.js:192` стоит
`const API = window.desktop || httpApi;` — в Tauri `window.desktop` создаёт
этот мост, и все 130 команд идут в Rust. Пока команда не перенесена, она
отвечает понятной ошибкой, а не молча ломает окно.

### Бэкапы, обои и свои окна

Бэкапы: архив собирает 7-Zip (LZMA2, `-mx=9`, словарь 64 МБ, тома по желанию).
Если бинарника рядом нет — панель **не ломается**, архив пишется своим zip с
deflate 9, а человеку честно сообщается причина. `.zip` и `.tar.gz`
восстанавливаются всегда. Перед восстановлением делается страховочная копия
текущего состояния, сервер при этом останавливается и (по желанию) запускается
снова — данные сервера не теряются.

Настольный режим окна: окно Tauri показывает ту же страницу через сервер
панели, поэтому «настольность» интерфейс узнаёт по ответу ядра (`mode:
desktop`) — диалоги, автозапуск и обои работают и в окне, и в браузере на том
же компьютере.

Обои: выбранный файл копируется в папку данных панели и отдаётся по
`/api/wall/<имя>`, поэтому фон работает и в окне, и в браузере. Палитра под фон
считается по тому же алгоритму, что в 1.26.0: уменьшение до 64×64, корзины по
16 оттенков, акцент — самая насыщенная и частая корзина.

Свои окна: системных MessageBox в панели нет — вопрос рисует интерфейс
событием `ui:ask`, ядро ждёт ответа (пять минут) и получает его как `ui:answer`.

### Поиск серверов, иконки, автозапуск

Поиск серверов перенесён из `core/scan.js` один в один: те же признаки
(`server.properties`, `eula.txt`, jar сервера, `plugins/`, `mods/`, `world/`,
скрипты запуска, `package.json`, `requirements.txt`, exe), те же веса и та же
предлагаемая команда запуска. Из настоящего сервера вглубь панель не идёт, из
папки плагинов — идёт; сама панель в результаты не попадает. Найденное сразу
уходит в интерфейс событиями `scan-found`, ход — `scan-progress`, отмена —
`scan:cancel`.

Иконки: PNG читается и пишется своим кодеком (`image.rs`, сжатие берёт из
`deflate`), иконка сервера сохраняется ровно 64×64 — как ждёт Minecraft.
JPEG и палитровые PNG панель не читает и честно об этом говорит: свой декодер
JPEG — это отдельный проект, а иконки делают в PNG.

Автозапуск: на Windows — запись в `HKCU\...\Run`, на Linux — файл
`~/.config/autostart/omnipanel.desktop`. Прав администратора не нужно.
Выбор файла и папки — системный диалог (PowerShell/WinForms, zenity, osascript),
потому что диски и избранное система показывает лучше любой панели.

### Синхронизация и обновления — как это работает

*Сервер уезжает в репозиторий архивом.* Папка складывается в ZIP своим
упаковщиком (DEFLATE), архив режется на части по 20 МБ, и каждая часть уходит
отдельным файлом вместе с `.omnipanel/манифест.json`. Причина прежняя: GitHub
отвечает `422 input was too large`, если отправить тело побольше, а base64
раздувает часть почти на треть. После успешной распаковки части удаляются из
репозитория — он работает как канал, а не как склад.

*Формат совместим с прежней панелью:* те же имена (`.omnipanel/сервер.7z`,
`.omnipanel/сервер.zip`, `манифест.json`), то же поле `parts` с `sha256`.
Поэтому репозиторий, отправленный версией 1.26.0, забирается Rust-сборкой, и
наоборот. Если в репозитории лежит `.7z`, а `7za.exe` рядом нет — панель честно
говорит об этом, а не оставляет пустую папку.

*GitLab — такой же провайдер.* Ветка, дерево, файлы и один коммит на всю
отправку (вместо десятков запросов по файлам) — поэтому большие миры уходят
без 422. Токен GitLab хранится отдельно от аккаунта GitHub.

*Токен живёт только в запросе.* Он попадает в заголовок `Authorization`
(GitHub) или `PRIVATE-TOKEN` (GitLab) и больше никуда: в файл настроек — только
сам токен, в интерфейс — маска `••••••••`, в логи — ничего.

*Обновления.* `upd:check` смотрит `update.json` в ветке и последний релиз GitHub,
берёт свежее. Код ставится сам: скачивается архив, сверяется SHA-256, старые
файлы панели копируются в `OmniPanelData/backups/updates`, и только потом
раскладываются новые. Папки `OmniPanelData`, `data`, `backups`, `tps`, `logs`,
`updates` и файлы `servers.json`, `panel.json` не трогаются никогда — даже если
они случайно окажутся внутри архива. Полная сборка скачивается только по
согласию; пока серверы работают, установка откладывается.

Архивы: свой разбор ZIP и свой распаковщик DEFLATE — панель открывает `paper.jar`,
`plugins/*.jar` и обычные zip, не тащя внешних библиотек. Проверено на архивах,
собранных настоящим архиватором: все девять уровней сжатия, метод 0, файл на 640 КБ,
кириллица в именах, совпадение CRC32.

Настройки `server.properties`: **64 поля**, и они не написаны в Rust руками —
`node tools/gen-props-schema.js` собирает `props_schema.rs` из `ui/props-schema.js`,
того самого файла, по которому рисуется окно настроек. Один источник — окно и ядро
не разъедутся.

Две мелочи, без которых интерфейс ломался бы молча:

* файловые каналы **не бросают ошибку**, а отдают `{ok:false, error}` — интерфейс
  проверяет `res.ok === false || res.error` (как `fsWrap` в прежнем `main.js`);
* у сервера без `cwd` канал файлов отвечает `«У сервера не задана рабочая папка»`,
  а не пустым списком.

### Панель на Rust уже запускается

```
./rust/собрать.sh run
→ OmniPanel на Rust 0.1.0 — интерфейс: .../ui
  адрес:  http://127.0.0.1:47800/
```

Rust сам отдаёт настоящий интерфейс панели (`ui/index.html`, 82 КБ) и отвечает
на его запросы: в `ui/app.js` уже есть `httpApi`, поэтому интерфейс работает
на Rust без единой правки в нём. Что перенесено — работает по-настоящему
(список серверов, запуск, живой лог, файлы, архивы, порты, настройки, баны, TPS);
что нет — отвечает понятным текстом, а не молчит.

Скрипт `rust/собрать.sh` сам скачивает Rust 1.91.0 рядом с панелью, если его нет
(без прав администратора; 1.91 нужен для TLS-зависимости `ureq`).
Тесты: `./rust/собрать.sh test` → **244 зелёных** (и 4 теста установщика).

### Окно и трей

`src-tauri/` — окно на Tauri 2: рамки Windows нет (шапку рисует сам интерфейс),
трей с меню «Открыть панель / Свернуть в трей / Выход», кнопка «закрыть»
в шапке уводит панель в трей, F11 переключает полный экран. Окно показывает
ту же страницу, которую отдаёт HTTP-режим, — поэтому в нём сразу работают все
перенесённые каналы.

**Важно:** сам крейт `src-tauri` в песочнице не собирается — для Tauri под
Windows нужны MSVC и WebView2, их здесь нет. Вся логика «что происходит по
кнопке» вынесена в ядро (`src/window.rs`) и проверена 10 тестами; оконный слой
собирается вашим скриптом `rust/собрать-под-windows.ps1` — он сам увидит
`src-tauri` и соберёт окно вместо консольной панели.

## 2. Два решения, которые поменяли план

**Сервер запускается строкой команды через оболочку, а не «java + jar».**
В панели `core/manager.js:398` стоит `spawn(srv.command, [], { shell: true })`.
Значит в Rust: `sh -c "<команда>"` (на Windows `cmd /C "<команда>"`).
Так работают и `java -jar server.jar nogui`, и `start.bat`, и `./run.sh`,
и питон-боты — то есть ровно то, что у игроков в настройках уже написано.

**Состояний только три: `stopped`, `running`, `stopping`.**
В интерфейсе (`ui/app.js:2888`) других нет, поэтому ядро не выдумывает
`starting`: сервер считается работающим сразу после запуска, как и раньше.

## 3. Как проверить

```bash
cd rust/omnipanel-core
sh ../../rustenv.sh test        # сам поставит Rust 1.91.0, если его нет
```

Ожидаемо: `244 passed; 0 failed` за ~35 секунд (тесты поднимают настоящие
процессы, ждут живой лог и мягкую остановку; синхронизация и обновления
разговаривают со своим HTTP-сервером на 127.0.0.1 — ни одного запроса в
настоящий GitHub).

Если Rust пропал (папка `build/` не переживает снапшот), ставим заново:

`rustenv.sh` ставит его сам: в `~/build/tc` (это не /tmp на 1 ГБ и не git),
либо в `$OMNI_TC`, если переменная задана.

Оценка целиком — 2–4 месяца. Промежуточные шаги безопасны: пока Rust-сборка
не догнала панель, обновления продолжают ставиться на текущую версию.

### Что ещё не перенесено и почему

Команд не осталось. Что осталось во всём переезде:

* **окно Tauri и установщик** — код написан (`src-tauri`, `rust/omnipanel-setup`),
  собрать можно только на Windows: нужны MSVC и WebView2.
**`load` больше не в этом списке:** боты перенесены целиком и проверены на
живом протоколе — тест поднимает сервер Minecraft на 127.0.0.1 и требует,
чтобы бот прошёл рукопожатие, вход со сжатием, фазу настройки, ответил на
`keep_alive`, пошёл и написал в чат. Числа пакетов при этом совпадают с
таблицами версий, а не «примерно похожи».

События (`toast`, `upd:*`, `scan-found`, `move-progress`, `ui:ask`…) Rust уже
отправляет в интерфейс: в HTTP-режиме — потоком `/api/events`, в окне Tauri —
через тот же поток. Отдельные команды для них не нужны.

## Что поправлено в 1.28.0 по следам первой установки

- **Картинки.** Интерфейс ссылается на иконки и обои как `../assets/…` — в окне
  это адрес `/assets/…`. Сервер панели отдавал только папку `ui` и отвечал 404,
  поэтому логотип, иконки и обои были пустыми. Теперь `PanelServer::with_assets`
  отдаёт папку `assets` рядом с программой (окно и консольный режим).
- **Окно.** Открывается сразу развёрнутым на весь экран; ответ на `win:toggleMax`
  содержит настоящее состояние (`{ok, state}`), иначе интерфейс считал, что окно
  не отозвалось, и уходил в полноэкранный режим браузера.
- **Установщик.** Вместо тихой распаковки — окно мастера (`rust/omnipanel-setup/installer.ps1`):
  куда ставить, выбор папки, переключатель ярлыка, «Установить»/«Запустить».
  Ставится в выбранную папку, пишется в «Программы и компоненты», удаляется
  тем же exe с `--uninstall`.
- **Запуск серверов.** Команда уходит в `cmd` одной строкой (`raw_arg`), а не
  через экранирование Rust: команды с кавычками в путях раньше ломались. Если
  процесс упал сразу, в лог пишется причина, а не просто «процесс завершён».
- **Версия.** Номер версии теперь пишется во все три `Cargo.toml` и в
  `tauri.conf.json`; сборка проверяет, что в exe попала именно эта версия.

### 1.29.0 — почему иконки «не грузились» после установки 1.28.0

Причина не в картинках, а в установщике: если панель уже стояла, установщик
**не показывал мастер и не распаковывал новые файлы** — просто запускал старую
версию. Поэтому в окне оставался прежний exe с 404 на `/assets/…`.

Что исправлено:
- установщик показывает мастер **всегда**, когда внутри есть панель;
- перед распаковкой закрывает запущенную панель (`taskkill`), иначе Windows не
  даёт перезаписать её файлы;
- в журнале мастера видно, что это обновление уже стоящей панели;
- картинки ищутся в нескольких папках: рядом с exe, на уровень выше, в ресурсах,
  в текущей папке — и путь пишется в журнал запуска;
- добавлены тесты: картинки из второй папки, отсутствие папки не ломает панель.

### 1.30.0 — кнопка «Обновить и перезапустить»

Раньше она ставила только архив кода (`dist/OmniPanel-code.zip`), которого в
релизах Rust-сборки нет — кнопка оставалась серой и ничего не делала.

Теперь `upd:apply` работает в два шага:
1. если в релизе есть архив кода — ставит его (так обновляется панель на Electron);
2. иначе `Updater::apply_setup` скачивает `OmniPanel-Setup-<версия>.exe`,
   запускает его на **ту же папку** с ключами `--install-dir <папка> --no-desktop --no-kill`,
   и просит окно закрыться — установщик подменяет файлы и поднимает панель заново.

С работающими серверами обновление не начинается: сначала просит их остановить
(«не ломать серверы»). Установщик с `--no-kill` не убивает панель, а ждёт, пока
Windows отпустит exe (до 10 секунд), и только потом распаковывает.

### Защита от «свежего» кэша сборки

`Swatinem/rust-cache` восстанавливает `target` с новыми временами файлов, и
cargo может счесть готовый exe «свежим» — тогда в релиз уедет прошлая версия
(так уже было с окном). Теперь перед сборкой чистятся все три пакета
(`cargo clean -p omnipanel / -p omnipanel-core / -p omnipanel-setup`), а после
сборки проверяется, что в **каждом** exe есть номер текущей версии.

Мелочь на будущее: строки в бинарнике линкер склеивает (`--no-kill` хранится
как `--no-kil` + хвост общей строки), поэтому проверять наличие ключей лучше по
номеру версии, а не по тексту ключа.

Установщик собран как оконная программа (`windows_subsystem = "windows"`), и

провалом. Проверено на поломке: скрипт ловит «cannot find function `shortcuts`».

### 1.38.0 — автообновление действительно проверяет

Жалоба «автообновление не работает вообще» оказалась точной: в Rust-сборке
проверку запускал **только человек** кнопкой в настройках.

**Что было не так.**

| где | что |
| --- | --- |
| ядро | у `Updater` был метод `auto()`, маршрут `/api/upd/auto` тоже был — но не вызывал их никто: ни при запуске, ни по таймеру |
| ядро | события `upd:state`, `upd:available`, `upd:progress`, `upd:ready` окно ждало, а ядро не отправляло ни одного — плашка «доступно обновление» не могла появиться в принципе |
| интерфейс | у клиента не было метода `updAuto`, поэтому кнопки и таймеры тоже ни к чему не приводили |

На Electron это работало (проверка через 3,5 с после запуска и дальше раз в
20 минут), при переезде на Rust эти две строчки не перенесли.

**Что сделано.**

| где | что |
| --- | --- |
| `update.rs` | `CHECK_EVERY` = 20 минут, `FIRST_CHECK` = 10 секунд; `auto_announce` — тихая проверка, которая ещё и рассказывает интерфейсу: `upd:state` → `upd:available` → `upd:ready` |
| `app.rs` | `App::start_auto_update()` — поток: первая проверка через 10 с, дальше раз в 20 минут, с учётом переключателей «авто» и «ставить сам» |
| `main.rs`, `src-tauri/main.rs` | поток запускается и в консольном ядре, и в окне |
| `app.rs`, `http.rs` | последняя проверка запоминается и отдаётся странице сразу при подключении — иначе панель, открытая после проверки, ждала бы плашку 20 минут |
| `ui/app.js` | когда код поставился сам, появляется уведомление «Обновлено до …» |
| `tests/update.rs` | четыре теста: тихая проверка сообщает окну, выключенная — молчит, установщик сам не запускается, работающие серверы откладывают обновление |
| `tests/http.rs` | тест: страница, подключившаяся после проверки, сразу получает `upd:state` |

**Как теперь.** Открыли панель → через 10 секунд она сама спрашивает GitHub.
Вышла новая версия → в шапке загорается плашка «обновление 1.38.0» и
появляется уведомление; в настройках остаётся нажать «Обновить и
перезапустить». Дальше проверка повторяется каждые 20 минут. Код (архив
`OmniPanel-code.zip`) ставится сам и только когда серверы стоят — мир на
половине сохранения не оборвётся. Установщик молча не запускается никогда:
это перезапуск панели, на него нужно согласие.

Проверено на живом ядре: с подменённым GitHub (объявлена версия 1.38.0)
панель через 10 секунд сама отправила в открытую страницу `upd:state` и
`upd:available`; с выключенным переключателем «авто» — не отправила ничего;
страница, подключившаяся уже после проверки, получила результат сразу.

### 1.39.0 — консоль обновляется, причина запуска видна

Жалоба «консоль не обновляется», а следом «видимо сам сервер не запускается».

**Что было.** Ядро отправляло строки журнала в другом виде, чем ждала страница:

| что отправляло ядро | что читает интерфейс |
| --- | --- |
| `{ id, line, state, at }` | `{ id, entry: { t, m, s } }` |
| история `/api/servers/<id>/logs` — массив **строк** | массив записей `{ t, m, s }` |
| TPS — как событие `state` с текстом `tps 19.9` | отдельное событие `tps` |

`entry` приходил `undefined`, обработчик падал на `entry.m` — и консоль не
показывала **ничего**: ни вывод сервера, ни ошибку запуска. Со стороны это и
выглядело как «сервер не запускается».

Попутно нашлась вторая причина молчания: у строки журнала не было уровня
(`system` / `stdout` / `stderr`), а разбор TPS с Paper не работал вообще —
`«TPS from last 1m, 5m, 15m: 19.9, …»` давало `None`, потому что в число
попадала запятая-разделитель. График TPS был пустым всегда.

**Что сделано.**

| где | что |
| --- | --- |
| `http.rs` | события в формате страницы: `log` → `{id, entry:{t,m,s}}`, `state` → `{id, state, pid, startedAt}`, отдельное `tps` → `{id, tps, history}` |
| `servers.rs` | событие несёт уровень строки, номер процесса и время запуска; TPS идёт своим видом события |
| `app.rs` | `server:logs` отдаёт записи `{t, m, s}`, а не строки |
| `servers.rs` | папки нет — пишем «Рабочая папка не найдена: …» до запуска, а не невнятную ошибку системы |
| `players.rs` | разбор TPS понимает `19.9, 20.0, 20.0`, `Mean TPS:` и `20.000 TPS` |
| `ui/app.js` | ошибка запуска не теряется: всплывающее сообщение «Не удалось запустить: …» |
| `tests` | строка журнала с уровнем, история записями, TPS своим событием, запуск с несуществующей папкой, разбор TPS (3 теста) |

**Проверено на живом ядре.** Сервер запущен настоящим процессом: в поток
событий пришли 9 строк `log` с `entry.m`, `entry.s` и временем; TPS пришёл
событием `tps` со значением 19.9 и историей; запуск с несуществующей папкой
вернул `{"ok":false,"error":"Рабочая папка не найдена: /нет/папки"}`.
