# Переезд OmniPanel на Rust — где мы сейчас

Версия панели на диске: **1.26.0**. Ничего в рабочей панели не сломано:
переезд идёт рядом, отдельным Rust-ядром, и подключается только тогда,
когда очередной кусок проверен тестами.

---

## 1. Что уже сделано

### Ядро `rust/omnipanel-core` — 165 тестов, все зелёные

Одна внешняя зависимость — `ureq 3` (HTTPS с rustls) для GitHub, GitLab и
обновлений. Всё остальное написано руками на стандартной библиотеке: JSON,
ZIP, DEFLATE, SHA-1, SHA-256.

### Мост «интерфейс → Rust»: `ui/tauri-bridge.js`

Собирается автоматически из `preload.js`:

```
node tools/gen-tauri-bridge.js
→ мост собран: ui/tauri-bridge.js
  всего методов: 153 (команды 130, события 21, отправка 2)
```

Это важно: интерфейс не переписывается. В `ui/app.js:192` стоит
`const API = window.desktop || httpApi;` — в Tauri `window.desktop` создаёт
этот мост, и все 130 команд идут в Rust. Пока команда не перенесена, она
отвечает понятной ошибкой, а не молча ломает окно.

### Поиск серверов, иконки, автозапуск

Поиск серверов перенесён из `core/scan.js` один в один: те же признаки
(`server.properties`, `eula.txt`, jar сервера, `plugins/`, `mods/`, `world/`,
скрипты запуска, `package.json`, `requirements.txt`, exe), те же веса и та же
предлагаемая команда запуска. Из настоящего сервера вглубь панель не идёт, из
папки плагинов — идёт; сама панель в результаты не попадает. Найденное сразу
уходит в интерфейс событиями `scan-found`, ход — `scan-progress`, отмена —
`scan:cancel`.

Иконки: PNG читается и пишется своим кодеком (`image.rs`, сжатие берёт из
`deflate`), иконка сервера сохраняется ровно 64×64 — как ждёт Minecraft.
JPEG и палитровые PNG панель не читает и честно об этом говорит: свой декодер
JPEG — это отдельный проект, а иконки делают в PNG.

Автозапуск: на Windows — запись в `HKCU\...\Run`, на Linux — файл
`~/.config/autostart/omnipanel.desktop`. Прав администратора не нужно.
Выбор файла и папки — системный диалог (PowerShell/WinForms, zenity, osascript),
потому что диски и избранное система показывает лучше любой панели.

### Синхронизация и обновления — как это работает

*Сервер уезжает в репозиторий архивом.* Папка складывается в ZIP своим
упаковщиком (DEFLATE), архив режется на части по 20 МБ, и каждая часть уходит
отдельным файлом вместе с `.omnipanel/манифест.json`. Причина прежняя: GitHub
отвечает `422 input was too large`, если отправить тело побольше, а base64
раздувает часть почти на треть. После успешной распаковки части удаляются из
репозитория — он работает как канал, а не как склад.

*Формат совместим с прежней панелью:* те же имена (`.omnipanel/сервер.7z`,
`.omnipanel/сервер.zip`, `манифест.json`), то же поле `parts` с `sha256`.
Поэтому репозиторий, отправленный версией 1.26.0, забирается Rust-сборкой, и
наоборот. Если в репозитории лежит `.7z`, а `7za.exe` рядом нет — панель честно
говорит об этом, а не оставляет пустую папку.

*GitLab — такой же провайдер.* Ветка, дерево, файлы и один коммит на всю
отправку (вместо десятков запросов по файлам) — поэтому большие миры уходят
без 422. Токен GitLab хранится отдельно от аккаунта GitHub.

*Токен живёт только в запросе.* Он попадает в заголовок `Authorization`
(GitHub) или `PRIVATE-TOKEN` (GitLab) и больше никуда: в файл настроек — только
сам токен, в интерфейс — маска `••••••••`, в логи — ничего.

*Обновления.* `upd:check` смотрит `update.json` в ветке и последний релиз GitHub,
берёт свежее. Код ставится сам: скачивается архив, сверяется SHA-256, старые
файлы панели копируются в `OmniPanelData/backups/updates`, и только потом
раскладываются новые. Папки `OmniPanelData`, `data`, `backups`, `tps`, `logs`,
`updates` и файлы `servers.json`, `panel.json` не трогаются никогда — даже если
они случайно окажутся внутри архива. Полная сборка скачивается только по
согласию; пока серверы работают, установка откладывается.

Архивы: свой разбор ZIP и свой распаковщик DEFLATE — панель открывает `paper.jar`,
`plugins/*.jar` и обычные zip, не тащя внешних библиотек. Проверено на архивах,
собранных настоящим архиватором: все девять уровней сжатия, метод 0, файл на 640 КБ,
кириллица в именах, совпадение CRC32.

Настройки `server.properties`: **64 поля**, и они не написаны в Rust руками —
`node tools/gen-props-schema.js` собирает `props_schema.rs` из `ui/props-schema.js`,
того самого файла, по которому рисуется окно настроек. Один источник — окно и ядро
не разъедутся.

Две мелочи, без которых интерфейс ломался бы молча:

* файловые каналы **не бросают ошибку**, а отдают `{ok:false, error}` — интерфейс
  проверяет `res.ok === false || res.error` (как `fsWrap` в прежнем `main.js`);
* у сервера без `cwd` канал файлов отвечает `«У сервера не задана рабочая папка»`,
  а не пустым списком.

### Панель на Rust уже запускается

```
./rust/собрать.sh run
→ OmniPanel на Rust 0.1.0 — интерфейс: .../ui
  адрес:  http://127.0.0.1:47800/
```

Rust сам отдаёт настоящий интерфейс панели (`ui/index.html`, 82 КБ) и отвечает
на его запросы: в `ui/app.js` уже есть `httpApi`, поэтому интерфейс работает
на Rust без единой правки в нём. Что перенесено — работает по-настоящему
(список серверов, запуск, живой лог, файлы, архивы, порты, настройки, баны, TPS);
что нет — отвечает понятным текстом, а не молчит.

Скрипт `rust/собрать.sh` сам скачивает Rust 1.91.0 рядом с панелью, если его нет
(без прав администратора; 1.91 нужен для TLS-зависимости `ureq`).
Тесты: `./rust/собрать.sh test` → **165 зелёных**.

### Окно и трей

`src-tauri/` — окно на Tauri 2: рамки Windows нет (шапку рисует сам интерфейс),
трей с меню «Открыть панель / Свернуть в трей / Выход», кнопка «закрыть»
в шапке уводит панель в трей, F11 переключает полный экран. Окно показывает
ту же страницу, которую отдаёт HTTP-режим, — поэтому в нём сразу работают все
перенесённые каналы.

**Важно:** сам крейт `src-tauri` в песочнице не собирается — для Tauri под
Windows нужны MSVC и WebView2, их здесь нет. Вся логика «что происходит по
кнопке» вынесена в ядро (`src/window.rs`) и проверена 10 тестами; оконный слой
собирается вашим скриптом `rust/собрать-под-windows.ps1` — он сам увидит
`src-tauri` и соберёт окно вместо консольной панели.

## 2. Два решения, которые поменяли план

**Сервер запускается строкой команды через оболочку, а не «java + jar».**
В панели `core/manager.js:398` стоит `spawn(srv.command, [], { shell: true })`.
Значит в Rust: `sh -c "<команда>"` (на Windows `cmd /C "<команда>"`).
Так работают и `java -jar server.jar nogui`, и `start.bat`, и `./run.sh`,
и питон-боты — то есть ровно то, что у игроков в настройках уже написано.

**Состояний только три: `stopped`, `running`, `stopping`.**
В интерфейсе (`ui/app.js:2888`) других нет, поэтому ядро не выдумывает
`starting`: сервер считается работающим сразу после запуска, как и раньше.

## 3. Как проверить

```bash
cd rust/omnipanel-core
sh ../../rustenv.sh test        # сам поставит Rust 1.91.0, если его нет
```

Ожидаемо: `165 passed; 0 failed` за ~20 секунд (тесты поднимают настоящие
процессы, ждут живой лог и мягкую остановку; синхронизация и обновления
разговаривают со своим HTTP-сервером на 127.0.0.1 — ни одного запроса в
настоящий GitHub).

Если Rust пропал (папка `build/` не переживает снапшот), ставим заново:

`rustenv.sh` ставит его сам: в `~/build/tc` (это не /tmp на 1 ГБ и не git),
либо в `$OMNI_TC`, если переменная задана.
