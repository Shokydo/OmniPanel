# Бэкапы и синхронизация

## Бэкапы

Кнопка «Создать бэкап» собирает **`.7z`** (LZMA2, словарь 64 МБ, твёрдый блок) — 7-Zip едет
внутри панели. Список бэкапов обновляется сразу, в консоль пишется имя файла, из какого объёма
сжат, во сколько раз плотнее и сколько в нём файлов. Старые `.zip` восстанавливаются так же,
как новые `.7z`.

* Уже сжатые `.jar` и `.mca` сильнее не ужимаются — это предел формата, а не настройки.
* Переключатель **«без libraries, versions и старых логов»** включён: эти папки сервер
  восстанавливает сам. Мир, плагины, конфиги и ядро попадают в архив всегда.
* Перед сборкой панель пишет в консоль, что занимает место.
* Бэкап, разбитый на части, в списке выглядит одной строкой с числом частей, а удаление
  чистит все тома.
* Хранится столько копий, сколько указано в настройках; есть авто-бэкап по расписанию
  и бэкап перед запуском.

## Синхронизация: GitHub или GitLab

В настройках сервера есть выбор **«Куда пересылать: GitHub / GitLab»**. Поток один и тот же:
панель собирает архив, режет его на части, отправляет; при заборе — скачивает части, сверяет
контрольные суммы, распаковывает и убирает архив из хранилища, чтобы место не росло.

### GitHub: лимит 95 МБ и ошибка «input was too large»

GitHub не принимает файлы больше 95 МБ, поэтому архив режется на части по **20 МБ**
(переопределяется переменной `OMNI_SPLIT_MB`). Если GitHub отвечает
`Sorry, your input was too large to process` (422) — тело запроса оказалось слишком большим
(base64 раздувает часть почти на треть). Панель видит это и **сама режет мельче**:
20 → 10 → 5 → 2 → 1 МБ, до трёх попыток, с записью в консоль
«GitHub не принял часть целиком — режу мельче: по 10 МБ…».

Отправка на GitHub:

1. панель упаковывает папку сервера в `.7z` и режет на части `.omnipanel/сервер.7z.001…`;
2. рядом кладётся `.omnipanel/манифест.json` с размерами и sha256 каждой части;
3. в строке состояния видно оба шага и каждую часть.

Забор с GitHub:

1. скачиваются все части («шаг 1 из 2»);
2. проверяется sha256 каждой части;
3. архив распаковывается в папку сервера («шаг 2 из 2»);
4. части и манифест **удаляются из репозитория одним коммитом**.

Нужен архив в репозитории как копия — включи переключатель «оставлять части архива
в репозитории».

### GitLab: хранилище пакетов вместо файлов репозитория

1. Архив 7-Zip режется на части (по 20 МБ) и заливается в **Package Registry** проекта:
   пакет `omnipanel-server`, версия — дата и время отправки.
2. Туда же кладётся `manifest.json`: список частей, размеры, sha256 каждой, число файлов.
3. Забор: панель находит свежий пакет, скачивает все части, сверяет суммы, распаковывает
   в папку сервера и **удаляет пакет из проекта**.
4. Повторная отправка без изменений ничего не отправляет: сравнивается отпечаток папки
   (число файлов, суммарный размер, самый свежий файл).

Токен GitLab: Personal Access Token с правом **`api`** (Settings → Access Tokens). Он хранится
в `panel.json` рядом с остальными настройками панели и никогда не попадает в файлы проектов
и в логи. Кнопка «Проверить» показывает проект, наличие ветки и доступность хранилища пакетов.

Адрес API своего GitLab задаётся переменной `OMNI_GITLAB_API`
(например `https://git.myserver.ru/api/v4`); по умолчанию — `https://gitlab.com/api/v4`.

### Что попадает в архив

* **уходит** — мир, плагины, конфиги, ядро, `server.properties`;
* **не уходит** — логи, кэш, бэкапы, `libraries`, `.git`.

### Отправка по файлам (только GitHub)

Если нужен пофайловый diff в репозитории, выключи переключатель «пересылать сервер одним
архивом». Тогда каждый файл едет отдельно, изменения считаются по хешу.

### Вход в GitHub и ошибка 409

Два способа: **по коду** (кнопка «Вход по коду») и **токеном** (запасной вариант).
Свой OAuth App заводить не нужно — используется встроенный публичный Client ID.
`409 Git Repository is empty` на пустом репозитории панель обходит сама: делает первый коммит
через Contents API и повторяет отправку.
